## 1. `/security-review` — the repo's own gate

Run over the branch's working tree with the repository's `security-review` skill.

**Outcome: one confirmed high-severity finding, against a fix this track had just written.**

The first pass of the SAML fix (NR-2026-001) had hardened the request id two ways: a minimum length,
and single-use redemption. The review pointed out that neither addresses the actual defect, because
**the id was still chosen by the caller** — the browser-facing endpoint was anonymous and created the
pending sign-in under whatever value it was given. An attacker never had to guess it. They pick a
value, send a colleague the link, the colleague's existing single-sign-on session completes the flow
on one click, and the attacker collects the session token.

That is the gate earning its place on the first run: entropy was the wrong axis, and the audit had
stopped one step short. The fix was reworked into four properties — server-minted id, approved-client
gate, explicit browser consent with an anti-forgery token, and client-bound single-use redemption —
and pinned by 23 test cases in `API.Tests/Security/SamlSignInFlowTest.cs`.

The review's other twenty-odd suspicions were investigated and did not survive; the reasons are worth
recording because they are the parts of the new code that were *checked* rather than merely written:

| Checked | Verdict |
|---|---|
| `AesGcm256` construction | Fresh salt and nonce per message, HKDF per-ciphertext key, full 128-bit tag, envelope length validated before slicing, key zeroed. No oracle: malformed, wrong-key and tampered are one outcome |
| `SecretProtector` v1→v2 migration | Dispatches on the actual prefix; round-trip-verifies before rewriting; leaves a foreign value byte-identical; nothing writes `enc:v1:` any more |
| `SafePathTool` sibling call sites | The other two places a caller-supplied id reaches a path (`VulnerabilitiesController` import routes) already gate on `StringCleaner.IsSafeFilename`. No unguarded sibling |
| `ExternalUrlPolicy` call sites | Both `Process.Start` sites guarded; whitespace rejected *before* `Uri.TryCreate`, which tolerates surrounding whitespace; no third call site |
| `ServerCertificatePolicy` default | Returns `null` (platform validation) unless explicitly opted in; `bool.TryParse` makes a missing or malformed value `false` |
| JWT revocation ordering | The `iat` check runs *after* signature validation, so it reads an already-authenticated claim |
| `BasicAuthenticationHandler` decode | `TryFromBase64String` buffer over-sized; first-colon split is RFC 7617-correct; every failure path routes through one `Unauthenticated` helper |
| `LoginAttemptTracker` eviction | Dropping an entry under the cap only *forgives* failures — it can never grant access |
| `OutboundUrlPolicy` bypass | `AllowAutoRedirect = false`, so a 302 to the metadata address cannot get past the check; every resolved address is examined, not the hostname |
| `security.yml` injection | `pull_request` not `pull_request_target`; `contents: read` at the top; `PR_BODY` only ever compared as a shell variable |

### The second pass

A second, adversarial review was run over the finished change set with the explicit instruction to
hunt for *incomplete fixes and functional regressions* rather than to re-confirm that the fixes
existed. It found four more, three of which no test could have seen:

* the API's Content-Security-Policy set `form-action 'none'`, and the reworked SSO flow had just
  added a consent **form** to an API-served page — so a browser would have refused the submission and
  **no desktop sign-in could complete**, while all 23 of the flow's own tests passed;
* the WebSite still resolved password-reset links by MD5 while the API had moved to SHA-256, so every
  synced reset link would have failed to resolve;
* the desktop client's certificate opt-in was readable from only one of the two places it can be set
  — and the error message told the operator to use the other one, so a client facing a self-signed
  server could never be configured;
* the lockout applied the same four-failure budget to the account and to the source address, which
  behind a reverse proxy is shared by everyone.

All four are fixed with regression tests and recorded in [FINDINGS.md](FINDINGS.md) §
"Regressions introduced by this track's own fixes". The pattern across both passes is consistent: a
control tested at the level it was written at looks correct, and the break appears one layer up.

## 4. Security headers — live scan

Captured against a running WebSite instance on this host. The API's headers come from the same
`SecurityHeaderPolicy`, with the stricter `default-src 'none'` policy; it could not be started here
because it needs a MariaDB instance.

```
$ curl -sk -D - -o /dev/null https://127.0.0.1:6443/
HTTP/2 200
content-type: text/html; charset=utf-8
x-content-type-options: nosniff
x-frame-options: DENY
referrer-policy: no-referrer
x-permitted-cross-domain-policies: none
cross-origin-resource-policy: same-origin
strict-transport-security: max-age=15552000
content-security-policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
                         img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none';
                         frame-ancestors 'none'; base-uri 'self'; form-action 'self'
```

No `Server` header, no `X-Powered-By`. Verified that the headers also land on a **404**, which is the
case a middleware registered too late in the pipeline would miss:

```
$ curl -sk -D - -o /dev/null https://127.0.0.1:6443/no-such-page
HTTP/2 404
… all of the above present …
```

**The scan found a defect in this track's own fix.** The first version of the middleware removed
`Server` from the response header collection, and the scan still showed `server: Kestrel` — because
Kestrel writes that header at the transport layer, after the middleware pipeline is done with the
response. Suppressing it needs `KestrelServerOptions.AddServerHeader = false`, which is now set on
both hosts. A unit test over the policy object could not have caught this; running it did.

The `content-security-policy` above also reflects a correction: the API's variant originally carried
`form-action 'none'`, which would have made a browser refuse to submit the SSO consent form the API
itself serves. It is `form-action 'self'` now — see §1, "The second pass".

## 5. TLS — live scan

```
$ for v in tls1 tls1_1 tls1_2 tls1_3; do openssl s_client -connect 127.0.0.1:6443 -$v; done
tls1     refused
tls1_1   refused
tls1_2   ACCEPTED
tls1_3   refused        ← platform, not configuration; see below

$ openssl s_client -connect 127.0.0.1:6443
New, TLSv1.2, Cipher is ECDHE-RSA-AES256-GCM-SHA384
```

TLS 1.0 and 1.1 are refused, which is the configured floor working. TLS 1.3 was also refused **on
this host**: .NET's TLS stack on macOS does not offer 1.3 in the server role, so the platform, not
`Security:Tls:MinimumVersion`, is the limit. On the Linux deployment target 1.3 is available and is
preferred.

That result is itself an argument for the decision recorded in
[DATA_PROTECTION.md](DATA_PROTECTION.md) §2: the listener previously pinned TLS **1.3 only**, which
on a host like this one would have served *nothing at all*. Allowing 1.2 alongside 1.3 — with
1.0/1.1 unreachable through configuration — is why this instance serves at all, and
`Security:Tls:MinimumVersion=Tls13` remains available for an installation that controls its clients.

## 7. What was not measured

Stated so absence is not read as a clean result.

* **CodeQL** was not run locally — it is a GitHub Actions-hosted analysis. The workflow is committed
  and will produce the first SAST baseline on the next push. Its findings are triaged into
  [FINDINGS.md](FINDINGS.md) per §7.5.1.
* **gitleaks** was not run locally (not installed). The manual sweep above covers the working tree;
  the committed gate covers the full history from the next push, with `fetch-depth: 0`.
* **A live API header and TLS scan.** The API needs a MariaDB instance. Its middleware is the same
  code path as the WebSite's, verified above, with a stricter CSP; the policy object itself is
  unit-tested.
* **The desktop client could not be launched.** Avalonia.Native cannot start its render timer in this
  environment, so every GUIClient change in this track is **compile- and lint-verified only** —
  including the SSO flow change and both certificate-validation fixes. That is a real limitation of
  this baseline, not a formality: `LoginViewModel.ExecuteSsoLogin` now calls a new endpoint and shows
  a new localized message, and neither has been seen on screen.
* **Fuzzing of the scan-file parsers.** §7.1.2 suggests fuzzing the Nessus XML parser. Not done. What
  was done instead is targeted: the three payload classes a hostile XML file actually uses (external
  file entity, external HTTP entity, entity expansion) are asserted against each live importer. A
  proper fuzzing campaign is a Track 8 item.
* **Penetration testing.** No third-party assessment. This is a code audit.

## 8. Re-audit

Per §7.5.3, at each **minor** release:

1. run `/security-review` over the release branch and commit the report as `baseline-<date>.md`;
2. run `./scripts/security/scan-dependencies.sh` and refresh the SBOM;
3. re-walk the changed areas of [ASVS_L2_CHECKLIST.md](ASVS_L2_CHECKLIST.md);
4. refresh the [threat model](THREAT_MODEL.md) deltas and re-date its accepted risks;
5. update [BURN_DOWN.md](BURN_DOWN.md).

**A release must not ship with an untriaged critical finding.** That is a release-checklist item, not
a suggestion.
